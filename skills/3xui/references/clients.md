# 客户端、动态订阅和排错

## 完成用户要用的订阅

历史部署曾只生成静态文件，漏开 Clash 订阅及独立端口；面板正常、节点能连，并不能证明动态订阅完成。

1. 确认客户端已启用且关联正确入站，核实到期、流量限制及订阅 ID。
2. 根据当前版本核实订阅总开关、监听地址/端口、公开访问地址和 TLS；核对 Compose 映射、防火墙及云安全组。
3. 用户需要 Clash/Mihomo 时启用对应功能；按需求启用主 SUB 的 UA 自动识别。历史 v3.11.0 有 `subClashEnable`、`subClashAutoDetect`，需要路由时有 `subClashEnableRouting`；这些是查找线索，不保证新版本字段不变。
4. 从真实出口拉取 SUB、专用 CLASH，并在已启用 UA 识别时检查主 SUB 的不同响应。响应体暂存受限文件，摘要不包含节点参数、UUID、密钥或订阅令牌。
5. 验证内容确实是目标格式，节点对应正确用户、地址和端口；解析成功后再启动临时客户端完成真实代理请求。不能只检查 HTTP 状态或手工制作的配置。

| 客户端/格式 | 交付与限制 |
| --- | --- |
| Mihomo / Clash Meta 系 | 优先原生 CLASH YAML；按目标内核校验节点、规则及 provider |
| 传统 Clash 内核 | 不假定支持 VLESS/REALITY；确认内核能力或与用户选择兼容方案 |
| Shadowrocket 小火箭 | 按实际版本验证 VLESS/REALITY/Vision；SUB 可更新节点，规则需单独配置 |
| 静态 VLESS URI、静态 YAML | 参数变化后需重新导出，不自动跟随面板 |

SUB 是通用节点订阅，并非仅供小火箭使用。节点订阅和完整路由配置的语义不同；小火箭的规则配置订阅需独立提供或选择，不能声称更新面板 SUB 就会获得国内直连规则。

## 名称、令牌和新增客户端

- 入站备注影响节点名称；客户端备注用于识别用户/设备；Clash 配置列表的订阅名称常可在客户端本地重命名。
- 订阅 ID 是访问令牌，不是展示名称。客户端可能把订阅 URL 末段作为默认名称，不应因此将令牌改成易猜的文字。
- 轮换订阅 ID 后按版本保存/生效机制验证新旧地址；客户端需替换完整订阅地址。不要把未知的订阅失败直接解释为需要重启。
- 已缓存的 UUID 和节点参数可能仍可连接。撤销节点访问需另外禁用客户端或轮换相应节点凭据，按用户授权执行。
- 同一个入站可以关联多个独立客户端；新增设备不自动要求新开端口或新增入站。下拉框为空先核实入站 API 与页面缓存。

## REALITY 握手兼容

同时核对服务端 Xray、客户端内核、传输方式、Vision flow、目标/SNI、公钥及 shortId。客户端能识别 VLESS URI 不代表能完成当前服务端握手。

2026-10-30 的 Xray 26.10.21 案例遇到新版 X25519MLKEM768 握手要求，Mihomo v1.19.33 的以下配置通过过真实连接测试：

```yaml
reality-opts:
  support-x25519mlkem768: true
```

这不是所有 REALITY 部署的通用修复。先看当前版本官方说明、生成配置和脱敏错误，再决定是否需要该参数及内核升级。历史 3x-ui v3.11.0 的 CLASH 输出已自动包含它，无需重复手工修改；转换器可能丢失参数，需检查实际输出。

安卓用户曾使用 `2.10.0.meta` 外壳并报告兼容与高延迟，不能据此外推其实际内核版本或认为所有安卓设备都有相同问题。其他客户端测试成功不等同于小火箭/iOS 设备通过。

## 国内、局域网直连和 DNS

只在用户需要时加入分流。明确客户端规则模式、代理组名称、规则来源、provider 格式、DNS 策略以及实际配置来源。

- 根据实际网络安排局域网、回环、链路本地、私网地址及必要管理地址直连；检查 IPv4/IPv6 与本地域名需求。
- 国内域名/IP 规则直连，其余流量按需求走指定代理组。分组名和兜底规则必须与真实订阅一致。
- 规则下载路径、更新周期和下载使用的代理要明确；首次加载必须能取到规则，避免代理依赖规则、规则又依赖代理的启动循环。
- DNS 解析路径应与路由和客户端能力相符，核实本地域名解析和代理域名解析，而非套用一份固定 DNS 模板。
- 修改维护副本后同步面板中的订阅路由设置，再拉取动态订阅验证；已有静态导出需单独更新。用户设备需刷新订阅、激活配置并使用规则模式，检查本地覆盖和覆写规则。

验证既看请求结果，也看实际路由命中：国内或局域网目标应 DIRECT，预期代理目标应走代理并符合出口预期。规则库分类有覆盖限制，不承诺所有国内站点都能自动识别。

## 常见故障的检查顺序

| 现象 | 优先检查 |
| --- | --- |
| `unsupported format type: mrs` | 内核是否支持 MRS、真实订阅 provider 格式、旧配置缓存 |
| 订阅 404/认证失败 | 新旧订阅 ID、完整路径、客户端状态及到期/限额 |
| 订阅超时 | HTTP/HTTPS、独立监听与映射、云侧入口、用户线路 |
| 订阅返回 200 但导入失败 | 是否返回 HTML 登录页、UA 识别、输出格式和内核支持 |
| 面板 502 | 错误来自面板、反向代理还是客户端系统代理/TUN；先核实真实部署架构 |
| REALITY 认证/握手失败 | 内核版本与参数、目标连通性、时间、相关日志 |
| 手机延迟高而服务端测试快 | 手机到 VPS 的线路、网络类型、握手、DNS/路由、服务端负载与出口分别测试 |

不支持 MRS 时可选择目标内核支持的 YAML 规则：同时匹配 URL、`format`、`behavior`、缓存扩展名和内容结构，不能只把扩展名改为 `.yaml`。修改后用空的临时缓存启动，证明 provider 能首次下载和解析，再验证分流。必要时建议升级受支持的客户端内核，但不能仅根据报错就盲目升级服务器。

面板 502 的历史案例在服务器本机没有复现，当时建议排查用户代理/TUN，但未证实具体原因；不能预设所有 502 都是客户端问题。低本机测试延迟同样不能证明手机线路正常。失败时要求不含敏感参数的具体错误、客户端内核和网络类型，停止盲目调节系统级网络参数。

测试客户端仅绑定回环地址，敏感配置限制权限；结束时只停止自己启动的临时进程、控制器和监听，不影响正式服务或用户已有客户端。
