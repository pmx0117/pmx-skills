# 软件安装与维护交接

将可运行的软件、可复现的部署配置和可接手的维护资料一起交付。与用户交流和维护文档默认使用中文。

## 目录与接手

- 默认部署到执行用户的 `~/app/<软件名>`，使用稳定、简短的目录名。用户明确指定其他位置时遵循用户选择。
- 操作前读取目标目录及适用父目录的 AGENTS.md，再读现有 README.md、当前状态和运维文档。已有部署先识别现状，避免重复初始化或覆盖用户改动。
- 将部署配置、持久化数据、备份入口及文档集中在该目录。软件包、容器运行时、systemd 单元等可能必须位于系统路径，记录所有目录外的系统改动，不承诺所有安装文件都在部署目录。
- 不把部署目录默认当作上游源码仓库，也不擅自初始化或推送 Git。
- 根目录只保留维护入口和部署入口：AGENTS.md、README.md、compose.yaml（适用时）、.env/.env.example、忽略规则。按实际用途创建 config/（非敏感配置）、data/（数据库和持久化数据）、secrets/（凭据、私钥、敏感导入文件）、backups/、scripts/、docs/。不预建无用途的空目录。
- Compose 留在根目录，挂载使用相对此处的路径，确保进入部署目录即可执行 docker compose。密钥文件可位于 secrets/，供 Compose 插值的 .env 可留根目录但须限制权限并排除提交。
- 迁移已有布局时先核对所有挂载、脚本、凭据路径和文档，做一致性备份；仅在需要时停服务，移动后同步所有引用并验证数据与功能。历史日志保留旧路径，并追加迁移映射。

## 需求与安装选择

- 从会话提炼目标、已授权范围、客户端和功能需求、网络暴露要求及用户明确偏好；缺失的必要信息简短询问，同时推进无依赖的检查。
- 查看系统/架构、现有服务、端口占用、权限、网络、磁盘内存和适用的 SELinux/防火墙状态。区分执行沙箱与宿主机，不能将沙箱限制解释成 VPS 故障。
- 根据官方当前文档选择原生包、发行二进制、容器或源码方式。适合持久服务时优先考虑可维护的 Compose，但不强制引入 Docker 或反向代理。
- 用户未指定版本时，核实官方稳定发布和适用平台，选择当前受支持、兼容的稳定版；记录核实时间、来源及选择依据。无法核实就明确标记，不猜版本号。
- 应用及容器镜像使用固定发布版本，适用时固定 digest；不使用会漂移的 latest 作为最终部署引用。运行时和插件采用官方支持的新稳定版，保留包管理器维护能力。
- 分别核实服务端、运行时、插件和客户端内核兼容性。应用外壳版本不等于内核版本；配置格式和协议兼容不能只用最新服务端推断。

## 实施

- 用户已要求安装时，在已有授权内推进到运行、配置所需功能和验证，不止生成计划。缺少执行权限时完成可准备的文件并如实说明阻塞，不反复尝试被策略禁止的提权。
- 管理入口首次启动默认限制本机，通过 SSH 隧道初始化；业务需要的公网入口按用户需求开放。用户已明确要求公网管理时遵循要求，并核对监听、端口映射、TLS 和访问方式。
- 逐项配置用户要用的功能；不能把登录页打开等同于整个任务完成。检查独立服务端口、功能开关、导出/订阅、客户端规则及用户会用到的格式。
- 凭据不进入聊天、工具输出、文档或版本控制。敏感值使用受限文件或适当的密钥存储，普通凭据文件一般 0600、目录 0700；文档只写存放位置、轮换和用户私下读取方法。先过滤日志和 API 响应再输出。
- 保留持久化数据和适用的 SELinux 挂载标签。根据软件支持的热加载机制应用配置；只有需要时重载或重启，避免每次改备注都中断服务。
- 升级、数据库迁移或可能破坏现有配置的操作前做一致性备份，记录旧镜像/版本和数据恢复方法。在线备份或停服务备份按软件能力选择，不能直接复制正在写入的数据库冒充有效备份。
- 不删除数据、不自动卸载原服务、不清理他人容器或无关防火墙配置。若变更失败，停止重复破坏性重试，保留原状态和诊断证据。

## 文档交付

在部署目录生成或维护以下文件，具体字段及写法见 [references/documentation.md](references/documentation.md)。首次创建交接文档及补齐现有部署文档时读取该参考。

- `AGENTS.md`：后续代理的入口、需先阅读的文档及本项目特有的维护约束。
- `README.md`：软件用途、当前可用状态、访问方式和文档导航。
- `docs/current-state.md`：唯一权威的当前状态快照，含精确版本、有效配置、功能状态、验证证据和待办。
- `docs/requirements.md`：用户目标、明确需求、决策依据、已完成与待完成范围。
- `docs/operations.md`：实际可执行的启动停止、诊断、备份恢复、升级回滚方法。
- `docs/deployment-log.md`：按时间追加的变更记录，包括验证结果和未解决事项。

配置和适用的脚本同目录保存；只有确实减少重复或误操作时才编写脚本。补齐忽略规则，排除凭据、私钥、数据库、导入链接、敏感备份和运行时文件。

当前状态来自运行服务、有效配置及 API，不只来自当初写入的模板。明确配置来源的优先级及哪些修改需要重载；静态导出文件不会自动随面板更新时写清楚。

每次变更同步当前状态、相关需求、运维步骤和变更日志。历史记录允许保留当时状态，但操作指南不能让读者在新旧配置间猜测。README 尽量引用快照，减少版本等事实在多处重复。

## 验证与结束

- 按软件类型执行配置检查、健康检查及最小真实功能验证。使用 Compose 时运行 `docker compose config --quiet`；修改 shell 脚本时运行适用的 `bash -n`。
- 检查进程、日志、真实监听、持久化、重启策略。需要时验证服务/容器重启后的配置；不为例行验证擅自重启整台主机。
- 真实验证用户需求中的功能和客户端输出。服务器本机 HTTP 200、从服务器请求自身公网 IP、独立外网访问和用户设备实测是不同证据，不能互相替代。
- 客户端兼容失败先看具体内核/格式/协议错误；网络慢先区分服务器资源、服务出口、握手、DNS/规则和用户线路，不凭服务器本地延迟判断手机线路，也不盲目调整全机网络参数。
- 清理为验证启动的临时进程、控制器和监听，不影响正式服务。
- 结束时简短说明安装版本、实际完成状态、访问或私下取凭据的方法、文档路径、验证范围以及真正阻塞的事项。尚未启动或未通过验证时不宣称安装完成。
